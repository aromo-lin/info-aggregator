# 行业资讯聚合器 — 设计文档

- 日期：2026-11-17
- 状态：待确认（draft）
- 适用平台：macOS（Apple 芯片优先），桌面客户端

---

## 1. 意图与为什么

用户想偶尔、手动地了解某个行业或话题（如时尚资讯、某电商行业销售情况等），
需要从**小红书、微信公众号、以及公开官网**这几类来源抓取真实内容，再由
**大模型汇总整理**成直观的结果给自己看。

纯 HTTP 爬虫容易被反爬拦截，因此采用**真实浏览器 + 半自动化**：用用户自己的
账号、自己家里的住宅 IP，像真人一样登录浏览，关键步骤（登录 / 验证码）由用户
手动完成。这样在反爬面前成功率最高。

已通过一次性 spike 验证：小红书「登录态复用 → 搜索 → 翻页 → 点击卡片打开 →
读正文/图片」这条链路可行（见第 4 节 spike 经验）。

定位：**先做自己用的单机桌面工具**；架构为**未来商用化**（卖桌面软件给他人各自
在本机使用）留好接缝，但商用层本期不实现。

## 2. 目标 / 非目标 / 反目标

### 目标（本期要做）
- **桌面客户端**（Mac 优先），不碰代码，打开即用。

> **v1 范围（已与用户确认）**：三类信息源中，**小红书做扎实可靠**（已 spike 验证）；
> **微信公众号（指定链接）与公开官网先搭框架、尽力而为**，不保证每个站点都稳；
> 公众号正式开工前**先做一次小 spike** 验证可行性（其链接常有特殊环境要求、尚未验证）。

- **项目 / 分组管理**：可新建分组（如「时尚资讯」「电商销售」）；每组保存多个
  信息源；进组后勾选本次要跑哪几个，一键运行，无需重填。
- **信息源两种形态**：
  - 固定网址：每次去重新读该页最新内容。
  - 搜索动作：输入标签/关键词 → 翻结果 → 点开前 N 条读。
- **半自动抓取**：应用自带的真实浏览器可见运行；遇登录/验证码停下等用户手动过；
  **登录态持久保存并复用**，同一身份下次免登。
- **抓取内容可自定义**（每个信息源单独配置）：
  - 抓取条数 N；
  - 内容类型：图片 / 动图 / 视频 / 正文（多选）；
  - 评论：默认**不抓**，可手动开启；
  - 排序：按点赞多 / 按最新等；
  - 时间范围（如仅近期）。
- **以图片 / 动图为主的视觉化结果**：最终产出是一份**可视化报告**（图片、动图直接
  嵌入），而非大段纯文字。
- **续抓（第二轮）且去重**：每个信息源记住已抓过的笔记/文章，点"再抓一轮"时
  自动跳过已抓项，只取新内容。
- **AI 汇总两种模式，可自由切换**：
  - 模式①导出：把整理好的内容（文本+图片）导出 / 复制，供用户粘贴进自己平时的
    AI 聊天窗口；
  - 模式②API：填 API key 直接调用，**模型可自由切换**（Claude / OpenAI 等）。
- 结果可在应用内查看，并可导出。

### 非目标（本期不做）
- 云端托管抓取 / SaaS（浏览器必须本地跑，见第 3 节）。
- **微信公众号按标签搜索**——无可靠入口，不支持；仅支持用户把**指定公众号或具体
  文章链接**存进信息源，逐篇读取。
- 全自动零人工：强风控站点仍需用户手动过验证码。
- 商用层（授权校验、Windows 版、客服、配方云端下发）——本期只留接缝，不实现。
- 自动填写账号密码 / 自动破解验证码。

### 反目标（即使"能跑"也算失败）
- 因自动化行为激进导致用户账号被风控限流或封号。
- 抓取节奏过快、过于机械，触发平台拦截。
- 产出是难以快速消化的纯文字堆砌，不直观。

## 3. 约束

- **平台反爬**：小红书需半自动、"点击卡片式"打开（而非跳转 URL）、控制节奏；
  微信生态封闭，公众号无开放搜索入口。
- **真实浏览器必须在本地运行**：住宅 IP 伪装度最高、用户要亲手过验证码、登录态
  属于用户——放云端会更慢、更易被封、且把数据与法律风险揽到服务方。
- **法律与合规**：这类工具在国内有合规风险；**商用前需专业律师评估**。产品形态
  坚持"仅在用户本机、用户自己账号运行，不代任何人托管或转售数据"，以尽量把风险
  留在工具提供方而非代抓方。
- **抓取"配方"会随站点改版失效**，需设计成可独立更新的模块（这也是商用护城河：
  盗版连不上配方更新，几周内自然失效）。
- **浏览器内核分发**：Playwright 内核从官方 CDN 下载在国内可能很慢/卡（spike 中
  已遇到），正式版需内置或走镜像源。

## 4. 方案（Approaches）

考虑过的几条路：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A（选定）** | Electron 做 UI + Playwright 驱动自带 Chromium | 抓取引擎最稳，spike 已验证；代价是"应用窗口 + 浏览器窗口"两个窗口，体积较大 |
| B | Electron 内嵌 BrowserView + 注入脚本抓取 | 体验更整、体积更小；但翻页/点开等复杂操作靠注入 JS，更脆，动态页易出问题 |
| C | Tauri + sidecar / 浏览器插件 | 淘汰：Tauri 插件化抓取折腾、浏览器插件不符合"桌面客户端"定位 |

**选定 A。** 用户最在意、最难的恰是小红书"搜索+翻页+点进去读"，A 在这块明显更稳。

### spike 经验（直接影响设计）
- **登录态复用成立**：登录一次存入 profile，再次运行可免登。
- **"点击卡片打开浮层"可绕过小红书"安全限制"**；而"直接跳转笔记 URL"会被当场拦截
  —— 正式版读取详情**一律走点击卡片**。
- 小红书页面上的「最热」「半年内」等**筛选按钮选择器不稳、不可靠**；因此"按点赞多"
  "按日期（如 7 月后）"等筛选，**改为客户端读取卡片上的点赞数/日期，自行排序与过滤**。
- 用系统 Chrome 作内核会与用户日常 Chrome 冲突（"已在现有会话打开"），正式版应**自带
  独立内核**，与用户日常浏览器隔离。

## 5. 已决定的"怎么做"

### 技术栈
- **Electron**（应用 UI、项目管理、结果展示）+ **Playwright**（驱动自带 Chromium）。
- **自带独立浏览器内核**，不借用用户日常 Chrome；内核内置或走国内镜像源分发。

### 登录身份与会话
- 每个"登录身份"对应一个**持久化 profile 目录**，保存 cookie/session。
- 信息源表单里的"账号"是**选择用哪个已登录身份**的标签，**不代填密码/验证码**；
  首次登录由用户在可见浏览器里手动完成。

### 数据模型（概念层）
- 分组（Project） → 多个信息源（Source）。
- Source = { 类型: 固定URL | 搜索; 站点; 关键词或URL; 登录身份; 抓取配置; 去重记录 }。
- 抓取配置 = { 条数N; 内容类型[图片/动图/视频/正文]; 评论(默认关); 排序; 时间范围 }。
- 去重记录 = 该源已抓过的笔记/文章 ID 集合；续抓时排除。

### 抓取引擎流程（以小红书搜索源为例）
1. 用选定身份的 profile 打开浏览器；若未登录则停下等用户手动登录。
2. 进入搜索，滚动翻页加载。
3. 读取每张卡片的 标题 / 点赞数 / 日期 / 作者 / 封面。
4. **客户端按配置排序（如按点赞）并按时间范围过滤**，并剔除去重记录中的已抓项。
5. 对选中的前 N 条：**点击卡片打开浮层** → 抓取 图片 / 动图 / 视频封面 / 正文
   （评论可选）→ 关闭浮层 → 下一条。
6. 节奏随机化，模拟真人。
7. 把新抓的 ID 写入去重记录。

### 图片 / 视频处理
- 图片、动图：保存原图 URL 并本地缓存，用于在报告中直接展示。
- 视频：取**封面图 + 可播放链接**；完整下载为可选项，默认关（较重）。

### AI 汇总与产出
- **可视化报告始终由应用生成，不依赖 AI**：应用把抓到的图片/动图 + 正文 + 元数据
  （点赞、日期、作者、来源）自动拼成一份图文报告（HTML/Markdown，嵌入图片/动图），
  应用内查看并可导出。AI 的"文字综述"是报告顶部**额外的一段**。
- **模式①导出**：导出含图文的内容包（Markdown + 图片文件夹）供用户粘进自己的 AI 聊天
  窗口；用户拿到 AI 综述后，**可粘回应用**补进报告顶部，生成最终版。（综述可有可无，
  报告本身始终成立。）
- **模式②API**：填 key，调用可切换模型；多模态模型可直接"看"图片，综述自动写入报告。

### 为商用化预留的接缝（本期只留口，不实现）
- 把各站点"抓取配方"做成**独立、可更新的模块**（日后从服务器下发最新可用配方）。
- 预留**登录 / 授权校验位**（日后接入账号 + 订阅校验）。

## 7. 已确认的决定（审阅后补）

与用户确认：
1. **导出模式的报告闭环**：可视化图文报告**始终由应用生成**；AI 综述是额外一段，
   导出模式下用户可把外部 AI 的综述**粘回应用**补进报告顶部（见第 5 节）。
2. **v1 范围**：小红书做扎实；公众号/官网尽力而为，公众号开工前先小 spike 验证
   （见第 2 节）。

设计者拍板（我的决定，供交付时复核）：
3. **去重 ID 来源**：spike 中卡片链接已暴露稳定笔记 ID（形如 `/explore/<id>`），可在
   **不跳转**的前提下从卡片读出该 ID 用于去重；点击打开是另一回事。若某站点取不到官方
   ID，则退化为「标题+作者+日期」指纹哈希去重。
4. **多源运行并发**：默认**串行**（一次跑一个源、单浏览器），把风控/封号风险降到最低；
   慢但稳，符合"偶尔手动跑、可接受慢"。并行不列入 v1。
5. **登录身份粒度**：一个"身份" = **某站点上的某个账号**（按站点划分），各自独立 profile
   目录；不在同一 profile 内混装多站登录态，减少被单站风控牵连的面。
